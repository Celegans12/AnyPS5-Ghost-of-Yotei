### 1.2a The seam: v4t's list against M1a's `GpuBackend.h` (the header is the base)
- Everything v4t's §5 lists is carried by the M1a header, or not needed in the M1a design:
  - lifecycle, submits (queue in the call), suspend, idle, shaders, map/unmap/protect, host write/read, faults, window,
    CPU flips, present (a null buffer is a clear), frame dumps (`frame_ready`), log/fatal, clocks, title id, content
    version, guest-thread query: all in the header;
  - event queues: AnyPS5 keeps them; the backend raises interrupts (`raise_interrupt`), so v4t's `eq_trigger/eq_pin`
    and Kyty's `AddEqEvent` are not needed;
  - VideoOut: `flip_reserve/wait_room/ready/cancel`, `display_buffer`, `rendering_wait` cover v4t's
    `try_reserve/.../gpu_ready/release`; AnyPS5 keeps the C++ objects behind tokens;
  - static table: AnyPS5 maps the AGC driver block with Kyty's layout itself, so nothing crosses;
  - not carried, and why: `reserved_range` (Kyty's `TryClampReservedRangeSize` is diagnostics; the shim answers with
    committed ranges), `prt_aperture` (sparse reads zero-fill the uncommitted gaps from the mapping table, which is what
    Kyty's sparse reader does), `direct_memory_views` (aliases, diagnostics only: none reported), `title` (window title:
    AnyPS5's window), `vulkan_loader_lock` (under kyty no other Vulkan user exists in the process).
- **Added: `Aps5GpuDisplayBuffer.dcc_control`** (was `reserved`, same layout, ABI 1 kept). Kyty decodes a compressed
  display buffer only with its DCC control; AnyPS5's `DisplayBuffer` gets `dccControl` (default 0, set by
  `DescribeVideoOutBuffer` for compressed buffers only, no change for the old backend).
- The header is copied into Kyty's tree (`src/aps5/GpuBackend.h`); both copies must stay identical (sizes and the ABI
  version are checked at create).

### 1.3 Memory shim (`memoryShim.cpp`)
- Kyty's `kernel/memory.h` is kept as the header; the DLL implements the 26 functions graphics uses.
- **Mapping table** (`GuestMap`, replaces Kyty's `VirtualRanges` committed part and `GuestBackingStore`): filled by
  `memory_map` (AnyPS5's commit/map/direct/file maps, after the change) and emptied by `memory_unmap` (before it). A
  mapped range is split with the host's `direct_mapping` into direct pieces (with their backing offset) and private
  pieces (flexible, pool, file, shared memory). A direct mapping the table does not know (mapped before the backend
  existed, or never notified) is found by a host lookup on first use and logged ("found by lookup").
- Kyty's lock-free parts are kept: the committed-page bitmap for `ClampRangeSize` (TheCruZ origin, as in Kyty) and the
  per-thread 64 KiB backing-slot memo with the table generation.
- **Kept unchanged from `kernel/memory.cpp`:** the resource walker's ordinary/strict/ahead read hooks, the fast
  verifier, `TryReadBufferBacking`, `ClampRangeSize` with its invalid-address report, `ReadGuestPlain`,
  `GuestImageReadArmed`, `GuestBytesForKernelRead`, `InstallGpuResources`, `HandleGpuFault`. `GuardedGuestCopy` uses
  `ReadProcessMemory` (as v4t's MinGW build).
- **Backing reads and writes** (`TryReadBacking/TryWriteBacking/CompareBacking/BackingOffset`) go through AnyPS5's
  backing view, so they never fault and never see the tracker's protection, as on Kyty. Private (non-direct) memory
  has no backing view: those calls return false there (`WriteBacking` then exits, as Kyty's does for unbacked ranges).
- **Protection** (`ProtectGuestHostMemory`): the tracker's mode over the committed pieces of the range only (Kyty skips
  gaps), through the host's `protect_guest` (AnyPS5 orders it against its own mapping changes). One `VirtualProtect`
  cannot cross from one allocation to the next; Kyty maps one view per guest mapping, AnyPS5 maps a guest range as
  several views (128 KiB views at 0xa36c960000 in the world [M VirtualQueryEx of the hung v4b-k-w1 process]). A piece
  the host refuses whole is therefore protected again allocation by allocation (VirtualQuery walk, committed parts
  only); the backend's 10-s line counts these splits (72f2250b, after run v4b-k-w1).
- **The backing view is committed at start** (13.5 GiB, as Kyty's SEC_COMMIT store): AnyPS5's kyty mode commits on
  map only, and a BDA-fallback granule with an uncommitted page would be refused and read zero.
- `TryReadSparseBacking` zero-fills uncommitted gaps; `FindDirectMemoryAliases` (diagnostics) reports none;
  `GetDebugStats` (the overlay) zeros.

### 1.4 VideoOut bridge (`videoOutBridge.cpp`)
- Kyty's flip stays in the command stream: `SubmitFlipFromGpu` reserves at AnyPS5 (`flip_reserve`; `QUEUE_FULL` →
  Kyty waits with `WaitForSubmitSlot` = `flip_wait_room`) and records the copy of the display buffer into a presenter
  frame (`Presenter::PrepareFrame`, the image info built as Kyty's `BufferAttributeGroup::ImageInfo`, from
  `display_buffer`). Blank/black/unregistered flips get a blank frame (black unless BLANK).
- `CompleteFlip` (Kyty's deferred priority operation after the GPU work) queues the frame in a FIFO, then calls
  `flip_ready` (AnyPS5's `GpuReady`), under one ordering lock, so the FIFO order is AnyPS5's queue order.
- AnyPS5's presenter thread calls `present` once per flip, at its vblank: the bridge takes the next frame (a buffer
  address that differs is logged), refreshes the swapchain size from the window, reads the frame back for a frame dump
  when asked (`Presenter::ReadFrame`, BGRA8 to `frame_ready`), presents it and calls `presented`.
- CPU flips (`submit_flip`): reserved at AnyPS5, then `GuestGpu::SubmitFlipPreparation`, as Kyty's
  `sceVideoOutSubmitFlip`.
- `WaitFlipDone` = `rendering_wait`. AnyPS5 keeps flip status, flip events, buffer labels and pacing.

### 1.5 Backend table (`kytyBackend.cpp`)
- `create` (under the loader lock): sets the host table, allocates the state; nothing else.
- `start`: Kyty's fatal errors go to `host->fatal`; the shader map; settings (§2: `APS5_KYTY_<NAME>` → `KYTY_<NAME>`,
  then AnyPS5's exact-variant defaults); Kyty's release `ConfigOptions` at 1920×1080 with `readback_tiled_images`;
  Kyty's log (silent, as release); the backing view.
- `attach_window`: the first one creates the device (Kyty's `WindowContext::CreateVulkan` on AnyPS5's window: the
  process's `vulkan-1.dll`, the window's instance extensions and surface callback), the presenter, the VideoOut bridge
  and `RenderContext::InitializeGpu` (Kyty's GPU threads); this thread becomes Kyty's "main thread" (the renderer's
  constructors check it). Every range AnyPS5 mapped before is handed to `RenderContext::MapMemory`.
- `submit`: queue 0 → `GuestGpu::Submit`, 0x20-0x57 → `SubmitCompute`, on the guest's thread (Kyty's queues are
  locked: q50-q53 come from job threads); it waits only if the device does not exist yet.
- `memory_unmap/map`: `RenderContext::UnmapMemory/MapMemory` for GPU-visible ranges and the table, under one lock.
- `memory_protect`: `RenderContext::InvalidateMemory` over the range (GPU-written bytes downloaded first, then
  CPU-dirty): a guest store after AnyPS5's `VirtualProtect` replaced the tracker's protection is not lost. Kyty's own
  mprotect does nothing of the kind (the overwrite exists on Kyty too).
- `host_write_begin`: `InvalidateMemory` (as Kyty's kernel before a file read). No pin across the host write (Kyty has
  none either; §4).
- `host_read`: each page goes through `RenderContext::HandleFault(Read)` (download, image watch lifted), so a
  kernel-mode read does not fail on a no-access page.
- `handle_fault`: `HandleGpuFault` inside Kyty's `RetriedFaultScope`, as `KytyExceptionHandler`.
- Interrupts: `RenderContext::TriggerInterrupt` calls `host->raise_interrupt` directly (Kyty patch a314c34d); AnyPS5
  delivers to the guest's event queues on the calling thread (Z2).
- Z4: Kyty's stage threads pin themselves and `ReserveCores` sets the process default CPU sets on first stage-thread
  start (`emulatorConfig.cpp`), unchanged.

### 1.6 Threads, TLS and the fault path
- The DLL is an import of `libSceAgcDriver.prx`, so the loader maps it at process start: its static TLS exists for every
  thread, AnyPS5's guest threads included; `thread_local`s first touched on a guest thread are lazily initialised by
  the compiler's TLS wrappers. No DLL-attach work is needed per thread [E from the PE: native `.tls` directory, no TLS
  callbacks of ours; to be confirmed by the first fault served on a guest thread, which the backend logs].
- Kyty's threads (libc++ `std::thread`/`jthread`) get a 64 MiB stack reserve (`threadStacks.cpp` replaces the DLL's
  `__imp__beginthreadex` pointer): eboot.exe's 2 MiB reserve is what they would inherit otherwise, against
  kyty_emulator.exe's 64 MiB (deep recursion in shader translation).

## 4. Open items
Correctness / exactness (for the user's decision, none changed silently):
1. Shortcuts with no exact variant stay on (§2 rows 2, 5, 8 and the residual cases of row 4); `KYTY_SHADER_LOOP_LIMIT`
   left at Kyty's 65,536 (row 3, user decision); `sync_raw_image_buffers=false` equivalence not checked.
2. Private (non-direct) memory has no backing view in the DLL: `TryReadBacking/WriteBacking` answer false there
   (Kyty's own build has a backing for all of it). The BDA fallback and buffer reads of flexible memory therefore take
   the slower/zero paths. Not seen to fail in T1; world not yet known.
3. No pin across a host write (`host_write_begin` only invalidates; Kyty has none either).

Robustness:
4. Fatal paths: a Kyty fatal now ends through AnyPS5's `Fatal` (report, `abort`, fast fail). Any `_Exit`/`ExitProcess`
   from inside the process can still hang in libSceAgcDriver's static destructor `ProfileOutput()::output` (it waits for
   a thread ExitProcess already killed), and Windows then refuses `TerminateProcess` (v4b-k-w1). That is AnyPS5's
   (not this lane's) to fix; the harness reports it as RESTORE DEFERRED / RUN1080 FAIL 90.
5. Nested mapping changes: `memory_map` may arrive under AnyPS5's direct-memory lock; the shim never calls the host
   lookup from there, and the host lookup only try-locks (§3 t1a). A notification-less mapping is found by lookup on
   first use (0 so far).
6. The VideoOut FIFO assumes every reserved flip is presented once in AnyPS5's order; a flip AnyPS5 never presents (or
   an overlay bus) would misalign it (logged as an address mismatch, blank fallback).
7. Tracker protections that cross AnyPS5's views are split after a failed first try (one wasted syscall each); the 10-s
   line counts them. If the count is high, the cheaper fix is for AnyPS5 to report view boundaries (or map one view per
   mapping, as Kyty does).
8. `GpuBackend.h` exists twice (AnyPS5 and `kyty/src/aps5`); the ABI version and table sizes are checked at create.
9. The DLL is loaded (and its static init runs) even with the switch off; T1-off still matches.
10. The Vulkan loader lock v4t listed is not taken (under kyty no other Vulkan user is in the process).
11. First-chance C++ exceptions (0xe06d7363) appear in the logs from Kyty code paths that catch them (seen in t1d);
    harmless so far, noisy under a debugger.
12. Kyty's cache dir was seeded from v4t's `kyty_emulator.exe` cache (304 MB driver cache); the coordinator's note says
    clang/libc++ SPIR-V differs from clang-cl's, so this DLL warms its own entries (world load compiled cold). The
    pipeline cache is saved every 2-6 min (runs are killed, `shutdown` is not called).
13. Speed: 4.47 M tracker faults in a 10-min world run (§3.2) and the cold world load are the visible costs; not
    profiled in this lane.
