## 2. How it builds

As expected in the task: **source in-tree, still a separate DLL, built by the top-level build with llvm-mingw clang
and libc++.** I found no better way: GCC costs ×0.56-0.68 and AnyPS5 does not build with clang (v4t).

- `cmake/KytyGpu.cmake` (new, included by the top-level `CMakeLists.txt` on Windows) adds `core/kyty_gpu` as a CMake
  ExternalProject with its own compiler. The `libs` target depends on it and copies the DLL, without its debug
  sections, to `core/libs/libs/kyty_gpu.prx`, where the run scripts and the adapter already look.
- Switches (CMake cache):
  - `APS5_KYTY_GPU=ON|OFF`, default ON on Windows. ON with no toolchain stops the configure and says what to install;
    OFF builds AnyPS5 as before.
  - `APS5_LLVM_MINGW_ROOT=<dir>`, default the environment variable `LLVM_MINGW_ROOT`. Not needed on `PATH`.
  - `APS5_KYTY_GPU_DLL=<file>` still takes a prebuilt DLL instead (the lanes' out-of-tree builds keep working).
  - `APS5_KYTY_PGO=AUTO|OFF|GEN|USE` (§5), `APS5_KYTY_GPU_JOBS`, `APS5_KYTY_GPU_COMPILER_LAUNCHER` (default none: the
    DLL's objects would only push AnyPS5's entries out of the shared ccache).
  - All eight configure paths were tried in a scratch project (OFF, prebuilt, no root, bad root, root, root from the
    environment, USE without a profile, AUTO with a readable and an unreadable profile) [M].
- In the directory, the three owned build files are Kyty's, cut down to the DLL: no emulator, launcher, tests,
  FFmpeg, SDL build or FetchContent. Flags are Kyty's own from the imported `utils.cmake`, unchanged: Release, `-O3
  -march=x86-64-v3 -ffp-contract=off`, ThinLTO, libc++ static, native TLS. The compile line of a DLL object is the
  same as in the current out-of-tree build except for the include paths, the profile option and three defines of
  Zydis and xbyak [M both `build.ninja`]. The DLL imports the same 18 system DLLs and exports the same one symbol
  [M `llvm-objdump -p`].
- **The build's name (`cmake/treeVersion.cmake`).** Kyty names a build by its git HEAD, switches its pipeline cache
  off for a "-dirty" tree, and keys its warm list by that name. In AnyPS5's repository that would make every
  unrelated commit a new DLL revision (100-220 pipelines compiled at the next start) and any uncommitted file anywhere
  a cache-less run. In-tree the name is a hash over the git trees of `src`, `3rdparty`, `assets` and `CMakeLists.txt`
  of the directory, dirty only when a tracked file of those has changes. Checked: the NOTICE commit and the top-level
  hook-up commit leave it at `c5d7071` [M]. A source zip without git builds with the cache off.
- **What a fresh machine needs** beyond AnyPS5's own prerequisites: llvm-mingw 20261104 (ucrt, x86_64; clang 23.1.5)
  unpacked anywhere, and `glslangValidator` (Vulkan SDK; found on `PATH` or under `VULKAN_SDK`; 1.4.363.0 here). On
  this machine: `C:/ps5/toolchain/llvm-mingw-20261104` and `C:/VulkanSDK/1.4.363.0`. Nothing was downloaded or

## 5. PGO

**The finding: a clang profile is tied to the directory it was made in, unless the build says otherwise.** clang names
every function with internal linkage in a profile by the absolute path of its source file. A profile used from
another directory gives those functions nothing, and the build log is silent about it (clang's warning for it is off
by default).
- In the current profile `research/v4/o/pgo/kyty_gpu-f57b49c.profdata` that is 4,215 of 12,519 functions, 21.3 % of
  all block counts, 40 of the 200 hottest [M `llvm-profdata show`]. It applies fully to the DLL built in
  `kyty-src-wt/int` (the best build 06033d83), and only in part to a DLL built from any other worktree with it
  (v4e3's b1 was one; the coordinator passed this on at 00:55).
- The fix is one hidden clang option on the training and the using build:
  `-mllvm -static-func-full-module-prefix=false`. The names become `file.cpp;function`. It is in the in-tree
  `CMakeLists.txt` for both modes.

**Proven at a second path (your condition).** The profile was trained in `C:/ps5/AnyPS5-scratch/v4-tree` (vv-train1)
and used in `C:/ps5/AnyPS5-scratch/v4-tree-clean`:
- The shipped profile holds 12,517 functions; 4,213 are named by file and 0 of those carry a directory
  [M `logs/chain-v1.log`].
- The clean tree's whole DLL build ran with clang's missing-function report on (`APS5_KYTY_PGO_WARN_MISSING=ON`; it
  only prints). It reported 14,791 functions without profile data, the unused inline and template functions the
  instrumented binary never contained. **None of them is a function the profile knows: 0 of 14,791**
  [M `logs/pgo-warnings-clean1.txt`]. Two functions lost their data for a changed control flow, `StartPgoWriter` and
  `TraceFrameTime`: the same two as in every GEN/USE pair since lane v4o.
- 16 objects (the hot draw, cache, command-processor and seam files) were compiled again to LLVM IR with the clean
  build's own command line, once in the clean tree and once with the paths rewritten to the training tree. Both give
  **5,420 function definitions with profile data and 0 without**, object by object
  [M `logs/pgo-sample-clean1.tsv`, `pgo-sample-dev1.tsv`].
- Two controls show the count can fail [M `logs/pgo-control1-*.tsv`]. The two objects with the hash-mismatch
  functions each show exactly 1 definition without data. And six of the 16 objects compiled in the clean tree with
  the **old** profile (`kyty_gpu-f57b49c.profdata`, default naming, as a lane would use it from another worktree)
  give **720 definitions with data and 517 without**, against 1,275 and 0 with the shipped one: in
  `commandRecorder.cpp` 375 of 522 get nothing.

**Shipped in the tree (your choice 1):** `core/kyty_gpu/pgo/kyty_gpu.profdata`, 4,052,432 bytes, from the 900-s
counter file of vv-train1 (the instrumented in-tree DLL: start, intro, save load, river village; 53.5 presents/10 s
while instrumented; no fatal). `APS5_KYTY_PGO=AUTO` (the default) builds with it when the file exists and this clang
can read it, and without it otherwise, with a warning. The profile's hash is on every compile line, so a refreshed
profile rebuilds the DLL.
- **Stale profiles** are never wrong, only weaker: a function whose control flow changed gets no data, the rest keep
  theirs. `APS5_KYTY_PGO_WARN_MISSING=ON` lists them.
- **Refresh** before a publish that touched hot code: configure `-DAPS5_KYTY_PGO=GEN`, build, one 900-s run, merge
  the last complete counter file, commit, configure back to `AUTO`, build. `research/v4/v/chain-v1.sh` is that
  sequence; it took one guarded build (6 min) and one run.
- The profile is not part of the build's name (§2), so a refresh alone does not make the next start compile
  pipelines again: the clean build started with 0 pipelines to compile after the training run of the same sources
  [M vv-t1on].

**What the profile costs in git (your question 3).**
- One profile is 4.05-4.29 MB raw and 0.86 MB zlib-compressed, which is what a push carries for a new one
  [M three profiles of 11-09 and 11-10].
- In a repacked repository a refresh adds less, because git stores it as a delta against the last one: three
  successive profiles packed to 864, 1,156 and 1,312 KiB, so **+0.15 to +0.3 MB per refresh** [M `git gc
  --aggressive` on a temporary repository]. For scale: the whole import, 33 commits, is 3.3 MiB packed.
- **Would a profile outside git be simpler for readers? No.** In the tree the reader does nothing. Outside it, the
  build has to fetch a file pinned to the commit (a download step in the configure, a place that keeps every
  version) or the reader passes it by hand; whoever skips it gets the slower build without noticing, because a
  missing profile is not an error. It would be simpler for the repository, not for the reader. If the history
  matters more later, the option is already there: `-DAPS5_KYTY_PGO_PROFILE=<file>`.

## 7. Linux (your question 1): what a Linux build of `core/kyty_gpu/` would need

Nothing was built or ported; this is from reading (a read-only survey of the tree, the adapter diff
72af1e5ea23..519f59c6a2a and Kyty's original build files; line numbers in `research/v4/v/logs/linux-survey.md`).

- **One thing first, and it is not about the backend: AnyPS5's own Linux build most likely does not compile on
  `local/v4-int` today.** `Backend/src/KytyAdapter.cpp` is in `libSceAgcDriver`'s sources on every platform
  (`CMakeLists.txt:459`) and uses `SRWLOCK`, `VirtualProtect`, `EXCEPTION_POINTERS` and
  `AddVectoredExceptionHandler` outside any `#ifdef` (lines 257, 686, 775, 867); only `<windows.h>` and the DLL load
  are guarded [M read; **no Linux build was run**]. Before `yotei/best` moves, the Linux testers' old-backend build
  needs that file guarded (about half a day, with `linux_ci.sh`).
- **The backend's own code is mostly ready:** `src/common` and `src/graphics` carry Linux branches beside the Windows
  ones (Kyty builds on Linux): file I/O, virtual memory, timers, threads, the page manager. Windows-only with stubs
  on Linux: the core reservation and thread placement (`threads.cpp` `ReserveCores`, `gpuPlacement.cpp`, ~360 lines),
  the start-up trace, one thread-priority call. Those are performance and diagnostics, not blockers.
- **The seam (`src/aps5`, ours) is Windows-only, with no `#else` anywhere:** about 110 lines in four files. The
  Vulkan loader by `LoadLibraryW("vulkan-1.dll")`; the guest images found with `VirtualQuery`; the guarded copy by
  `ReadProcessMemory`; the protection walk across Windows allocations (`ProtectPiece`); `VirtualAlloc` to commit the
  backing view; the 64 MiB thread-stack hook (`threadStacks.cpp`); `__declspec(dllexport)`.
- **AnyPS5's side of the seam is Windows-only too:** the "kyty mode" of direct memory (one backing view), the map,
  unmap and protect notifications, `protect_guest`, the DLL load and the fault hook exist only in the Windows paths.
  Linux already keeps direct memory in one memfd, so the backing view is one more mapping; its SIGSEGV handlers do
  not call the backend yet, and where the backend's handler sits among them needs a design, as it did on Windows.
- **The build:** the three in-tree build files are Windows-only on purpose (they stop the configure elsewhere).
  Kyty's original files had the Linux side (GCC or clang, `-march=x86-64-v3`, pthread, dl). New on Linux: a shared
  object needs position-independent code in every static library it links, and hidden symbols for the libc++ inside.
- **The second toolchain may not be needed there.** clang with libc++ is needed on Windows for reasons that are
  MinGW's (emulated TLS, winpthreads, GCC's unwind-table stalls; v4t). Linux GCC has native TLS and native pthreads,
  and Kyty's own Linux builds use GCC or clang. Whether a GCC build is as fast on Linux is not measured by anyone here.
- **Rough size [E, from the survey's line counts]:** 600-1,000 lines in about eight places (seam 150-250, adapter
  150-250, direct memory and observers 90-180, fault routing 80-150, CMake 80-150, optional placement 300-450), plus
  the fault-order design and a T1 and world validation on Linux hardware, which we do not have. One to two weeks of
  a lane, with a tester's machine in the loop.

## 8. The re-import script

`research/v4/v/reimport.py` (git plumbing only: `ls-tree`, `cat-file --batch`, `fast-import`; no checkout and no
line-ending conversion on the way, so a blob has the same hash on both sides):
- `replay --aps5 <worktree> --tip <kyty commit>`: the base commit and one commit per first-parent Kyty-side commit.
  This made the first 29 commits of the branch in 4 s.
- `sync --aps5 <worktree> --tip <kyty commit> [--squash] [--dry-run]`: from the last imported commit to a new one,
  one commit per first-parent commit, or squashed when the history does not continue the last import. It leaves the
  three owned build files alone and prints their Kyty-side diff. It refuses when an imported file was edited in-tree.
- `verify --aps5 <worktree> --tip <kyty commit> [--rev <rev>]`: blob-by-blob compare; exit 0 when only the owned
  files differ.
- `notice --aps5 <worktree> [--write]`: the NOTICE text from the branch's own history.
- State: `research/v4/v/import-state.json` (base, last imported commit, the commit map).
- Tried without writing [M `sync --dry-run`]: `v4/x2` 797c6cae would arrive as 6 commits, `v4/e3` 950b813f as 4;
  neither touches an owned build file.
- New worktrees get their 31 submodules without network from `research/v4/v/setup-submodules.sh` (2.5 min).

> ### Building with the new GPU backend (Windows)

> **Build:**
> ```
> git submodule update --init --recursive

> ```
> - The configure prints `kyty_gpu.prx: core/kyty_gpu with <toolchain>, PGO USE`.
> - `kyty_gpu` is the new backend: about 4 minutes on an 8-core laptop. The second command builds the libraries and the
