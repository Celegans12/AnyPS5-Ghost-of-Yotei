Lane v4c. Offline only: the AnyPS5 frame captures were parsed with Python. There was no replay, no game run and no
GPU job. The one machine job was a three-file compile check of the patch branch, run through `machine_guard`. Nothing
was posted. PLAN, STATE and HANDOFF were not touched.

- **Captures:** `captures/cap-river17` (12 frames, boundaries 1016-1027), `cap-river18` (3 frames, 1045-1047) and
  `cap-river19` (3 frames, 1020-1022). All three were written by AnyPS5 `f5c5051432bc` in the river village at 4K. That is
  18 frames in all: 248 submissions, 662,445 packets and 4.91 M dwords walked, about 36.8 k packets per frame.
  - `libSceAgc` emission at `f5c5051432bc` is the same as at yotei/best `72af1e5ea23`. The only change in between is a
    diagnostic race guard in `Command/src/Packet.cpp` [M `git diff`].
- **Kyty:** KytyPS5-Yotei v0.1.5, `C:\ps5\kyty-src`, branch `v4/base` (`a2f25e1f`), read in my own worktree.
- **Tags:** [M] means measured from the captures or read in code (the source is named). [E] means an estimate.

### 0.3 Z3: the HLE JobManager is not used by Ghost of Yōtei; no fix needed

- **[M] 0 HLE JobManager ACBs per frame.**
  - Yōtei does not import `libSceJobManager` at all. None of the 11 JobManager exports AnyPS5 defines (`_ZN3sce3Job…`) is
    among eboot.bin's import NIDs.
  - eboot.bin names no `libSceJob*` module. Its only "JobManager" string is the game's own `CJobManager`.
  - No submission in the 18 frames has the HLE shape (≤80 dw with one dispatch, or a lone 8-dword RELEASE_MEM). All 248
    are the game's own named ACBs and DCBs ("Particle Update", "CS Cloth", "Proxy Set Cull", …).
- **The v4s/v4g premise does not hold for this title.** It said "Kyty loads the native module". Neither emulator runs any
  `libSceJobManager` code for Yōtei.
  - Kyty has no JobManager HLE.
  - Its sysmodule table loads only `libSceNpCppWebApi` from app0 (`libs/libSysmodule.cpp` l.27-30).
  - The game's `sce_module` holds only `libc.prx`.
- **ACQUIRE_MEM costs nothing in Kyty's CP.** `CpOpAcquireMem` checks the header (`c0055800` or `c0065800`) and returns
  (`pm4Handlers.cpp` l.1303-1308) [M code]. The global barriers come from three other packets
  (`RecordGlobalBarrier`: `EndRendering` + an all-commands `pipelineBarrier2`):
  - RELEASE_MEM (every path);
  - EVENT_WRITE CS/PS partial flush and the cache write-back events;
  - every WAIT_REG_MEM that passes.

  Also, every guest submission ends in one host `vkQueueSubmit` (`BufferFlush`).
- **What Kyty's CP will do per frame in this scene [M census, model]:** at least 13.8 host submissions (one per
  submission, plus one per slice resumed after a wait) and up to 858.6 global barriers:
  - RELEASE_MEM 166.5;
  - EVENT_WRITE 511.6;
  - waits that pass, up to 180.5.

  All of these come from the game's own packets. They are the same in kind as on Kyty standalone, because the game makes
  the same calls and the builders match packet for packet.
- **Recommendation: neither fix (0 lines).** For another title, the sizes would be:
  - **Batch per sync point in our HLE:** ~60-100 changed lines in `libSceJobManager/Export.cpp` plus one test, about 1
    agent-day [E].
    - It is only safe for compute items that are already runnable in the same `Advance()` pass. There is no guest "kick"
      call, so holding a job until the next sync point would delay its GPU start.
    - If that path were used, each HLE job ACB would cost Kyty one host submission (~20-50 µs of CP-thread CPU [E]) and
      no barrier. Each sync point would cost one barrier, one submission and one interrupt.
  - **Load the native module:** not available. The module is firmware, not game data, and Kyty does not do it either.

### 0.4 What the adapter lane (v4a) must know

1. **Vendor base:** `v4/base` plus the three patches (`v4/cp-patches` `5d5bdcc3`). Without patch 3 the first wait in
   the first frame stops the CP; without patch 1 the first release does.
2. **Queues in use:**
   - 0x00 gets one 30-dword DCB per frame, which chains 147-157 indirect buffers (~235 k dw; chain flags `0x0f3`).
   - The async queues: 0x20 (4.8 ACBs per frame), 0x30, 0x38, 0x48, 0x50, 0x51 (a 24-dword ACB that chains once), 0x52
     (2 ACBs per frame) and 0x53.
   - All of them are inside Kyty's 0x20-0x57 range. No submission carries flags.
   - There is no constant (CE) buffer: `GuestGpu::Submit(span, {})` is enough.
   - Submissions come from the render thread (q0, q20, q30, q38, q48) and from the game's job threads (q50-q53). The
     adapter's submit path must be thread-safe, which Kyty's `Enqueue` is.
3. **Interrupts (Z2):**
   - On q52, one RELEASE_MEM per frame has an interrupt (int_sel 2, context id 0x416, data 0x416). It is the only
     interrupting packet in the census.
   - Kyty raises it through `TriggerEopEventAtEndOfPipe`/`TriggerInterrupt(event_id, context_id)`.
   - The game imports `sceAgcDriverAddEqEvent`. The equeue routing and the context-id difference from v4s §1.3 apply
     here.
4. **Flip in the stream:**
   - On q0, each frame has one 4-dword rendering wait (handle 1, index n), then the frame's R_FLIP (`c004105c`, handle 1,
     mode 1).
   - The VideoOut bridge sees `WaitFlipDone(1, n)` and `CpOpFlip` as on Kyty.
   - The game also imports `sceAgcAcbSetFlip`, which emits the same packet on a compute queue. It is not seen in this
     scene.
5. **The COND_EXEC on q0** (one per frame, exec 50 dw) guards a block of waits: markers, wrappers and two WAIT_REG_MEMs.
   Its predicate address is `0x5000000090`. With patch 3 Kyty classifies it WaitOnly and never reads the predicate, as on
   Kyty standalone.
6. **The CP writes into command-buffer memory.** On q0, 74 times per frame, a 5-dword WRITE_DATA and a RELEASE_MEM with
   data_sel 1 (event 0x2d, 0x2b or 0x14) write into the payload of a 10-dword NOP in the same DCB, a label slot. All 74
   + 74 did so in cap-river18 frame 1 [M].
   - So the memory shim must accept CP label writes into pages that hold command buffers.
   - Kyty's `TryCpWriteThrough` path covers this on Kyty. It is the same game behaviour there.
7. **Interface surface the census confirms:**
   - the submit functions `sceAgcDriverSubmitDcb`, `SubmitAcb` and `AgrSubmitDcb`;
   - `AddEqEvent`, `SetTFRing`, `SetHsOffchipParam`, `RegisterResource` and `RegisterOwner`.

   That is the whole set of 8 driver imports [M `imports.txt`].

## 6. Method

1. **Capture reader (`capfmt.py`).** The format is `aps5-frame-capture 1`, from `FrameCapture.cpp`/`FrameRecorder.cpp`
   (yb-combo):
   - `calls.bin` holds the call records (kind, ordinal, time, thread, queue, address, dwords, values);
   - `memory.bin` holds 64-byte chunk headers and zstd payloads: snapshot runs of 64 KiB blocks (zero blocks skipped),
     then delta groups;
   - each `memory` call names the delta group written just before the next call.

   The reader keeps a page → delta-chunk index and an LRU of decompressed chunks, and reads guest memory as it was at any
   call.
2. **Walker (`census.py`).** It walks every submission from `frame-start` on, at its point in the call stream, with the
   memory overlay at that point.
   - Frames end at the `display-buffer` calls that the recorder writes at each frame boundary.
   - Each buffer is walked packet by packet. The walker follows INDIRECT_BUFFER calls (pushed), chains (the buffer's
     cursor is replaced, as Kyty does) and branches (both sides).
   - It records:
     - every packet as (frame, queue, name incl. custom code, length, header without the predicate bit);
     - sub-variants;
     - SET_*_REG offsets, and the (offset, value) lists behind the indirect register packets, read from guest memory;
     - non-type-3 dwords, fillers and packets after a chain;
     - per-submission summaries: ops, markers, barriers.

   A 3-frame capture takes about 15 s; 4,025 chunks were decompressed for the three.
3. **Kyty model (`kyty_cp.py`).** This is `ProcessPm4`'s loop:
   - type-2 `0x80000000` and one-dword fillers are skipped;
   - the opcode is taken from bits 15:8 with no type check;
   - bit 0 is cleared before the handler.

   Each `CpOp*` handler's `EXIT_NOT_IMPLEMENTED`/`EXIT` conditions and returned length are transcribed. So are the deeper
   checks on the paths the census reaches:
   - `ExecuteTriggerEvent` event types;
   - `WriteAtEndOfPipe`/`ClassifyEndOfPipe` for RELEASE_MEM;
   - the `WaitRegMem` op and function;
   - `DmaData` selectors;
   - the `WriteData` destination;
   - the `CopyData` selectors.

   `patched=True` applies the three patches.
4. **Registers (`kyty_regs.py`):** §4.
5. **Imports (`imports.py`):** NIDs computed as SHA1(name + 518D…) → LE 8 bytes → base64. This was checked on
   `sceAgcCbReleaseMem` = `wr23dPKyWc0` (AnyPS5 libSceAgcVsh's export table).
6. **Limits:**
   - The census covers the river village at 4K only (boundaries 1016-1047). The title, loading, menus and other areas
     are bounded only by the import list (§0.1), not seen.
   - The verdicts are a transcribed model of Kyty's asserts. Kyty's CP did not run on these streams.
   - Anything that depends on run-time state was not checked: GPU-written predicates, shader translation, resource
     formats. A replay through Kyty's CP would be the next step if one is wanted; it needs the adapter's memory shim.
