## 1. Design and why each switch is exact

### 1.1 `KYTY_PERF_EXACT_WALKER` and `KYTY_PERF_EXACT_FAULTS` (cache/exactTicks.h) [C]
- Exact write ticks are kept per written byte range (an interval map, as Kyty's own sync-timeline map), but only inside
  the 64 KiB granules such reads touched ("learned", at most 4,096 granules = 256 MiB, least recently read forgotten
  with its entries). Every granule tick raise (`NoteGpuWriteTick`: obtained writes, their final tick once recorded,
  image copies into buffers) also notes its range clipped to the learned granules at the same tick, so a covered
  byte's entry is never older than its newest write; bytes written before their granule was learned have no entry and
  use the granule tick. The map is kept whenever a switch can be on (set or listed by KYTY_LIVE_AB), so both A/B phases
  pay its upkeep (measured separately: PERF exact_reads `notes`).
- The read (inside BufferCache::ReadMemory's request, on the GPU thread, after the eager copies): every GPU-dirty
  interval of the ±4 MiB read window gets its exact tick, else its granule tick. It waits for the newest tick of the
  intervals it needs (the walker: its bytes; a fault: its pages) and the buffer's creation tick, if that tick is
  submitted and none of them is a write obtained but not recorded; otherwise the usual path runs unchanged. It
  publishes every interval finished by that tick (the window's if ≤ 1 MiB, else the access's pages', else the needed
  ones), by BAR read or GPU copy, with TryBarDownload's calls; pages left without GPU-dirty bytes are unmarked (a written
  fault page released to the CPU), the rest stay GPU-modified.
- Exact: each published interval's newest write is finished when it is read (its tick, exact or the granule's upper
  bound, is at most the waited tick; a write recorded later would have a newer tick), so its bytes are what the usual
  path publishes for it; unpublished bytes stay GPU-dirty and are synchronized when accessed. Only how long a read waits
  and which finished bytes it publishes change.
- Verify mode `KYTY_PERF_EXACT_VERIFY=<n>`: every n-th exact read of each kind submits the open buffer, waits for all
  recorded work and compares the published intervals (read again from the mapping) with guest memory through the
  backing view, before the pages change state.

### 1.2 `KYTY_PERF_GPU_POLL` (masterSemaphore.h) [C]
- On the GPU thread only: `MasterSemaphore::Wait` polls `vkGetSemaphoreCounterValue` with a pause backoff (≤ 64
  pauses, ~2 µs) instead of `vkWaitSemaphores`; `BarGpuRead` polls `vkGetFenceStatus` instead of `vkWaitForFences`. A
  wait unmet after 100 ms blocks as before. The exec thread runs on its own reserved core (Kyty's core reservation), so
  the spin takes no guest thread's time. Exact: only how the thread waits changes.
