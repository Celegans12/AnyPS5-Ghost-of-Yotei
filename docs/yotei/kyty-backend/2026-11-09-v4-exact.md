## 3. Step 2: BDA first-use zeros (X6) and memory without a backing view (v4b §4.2)

### 3.1 What the G2 build does [C]
- A shader's BDA access looks its 16 KiB page up in the flat page table (`spirvEmitterMemory.cpp`, `GetBdaPointer`).
  Entry 0: the load reads **0**, the store is dropped, and the page's bit is set in the fault buffer. The fault pass
  (`faultManager.cpp:269-554`) reads the bits at least a frame later and creates a buffer over the 2 MiB window
  (`KYTY_PERF_BDA_PROMOTE_KB=2048`).
- The BDA fallback (M06, `bufferCache.cpp:163-371`) gives a direct-memory page without a buffer an entry into the guest
  backing, imported as Vulkan host memory in 2 MiB granules, at most 1,536. A granule is imported only when the game's
  list (`<cache>/PPSA26344_01_008_000.bda_granules`) names it, when a direct download needs it, or after a shader read of
  it was reported as a miss (`WantFallback`): **that first read returned zero**. The list keeps the granules for the
  next session, so the zeros mostly hit the first session and new areas.
- Each fault pass prints `BDA_FAULT frame=… count=… fallback=… zeros=… backing=… committed=… reserved=… unmapped=…`
  (the zero pages by what the guest has there). That line is the zero-read counter; it was on in every G2 run.

### 3.3 The exact variant: `KYTY_FIX_BDA_FALLBACK_EAGER=<MiB>` (Kyty 023525bb)
- Under AnyPS5 all direct memory is one section with one backing view (13.5 GiB, committed at start by the shim). With
  the switch, the fallback imports that view in units of `<MiB>` (power of two, 2-4096) **when a direct mapping reaches
  the unit** (`QueueFallbackMap` → `WriteFallbackRange` → `FallbackEntry` with `want`), so every mapped direct page
  without a buffer has its fallback entry before any shader reads it; no BDA read of direct memory can return zero.
- The rest is unchanged: a page with a buffer uses the buffer; fallback-served misses still create buffers; unmaps clear
  the entries; downloads take the unit imports. The granule list is neither read nor written (2 MiB indices). Each
  unit's import is logged with its time (`FIX_BDA_FALLBACK_EAGER unit …`). A unit the driver refuses is logged, and its
  pages then miss as without the fallback (counted as backing zeros).
- What it costs: the imported units stay pinned host memory for the session (all mapped direct memory, rounded to
  units, instead of ~0.4 GB of granules), and the imports themselves (the G2 build spends 39-79 s of GPU-thread time on
  85-222 granule imports per run, `import_ms` [M, table above], mostly at start and during loads).
- Unset or 0: the G2 code path (2 MiB granules, the list, the cap).

## 4. Step 3: the loop cap

### 4.1 Where the cap is [C]
`KYTY_SHADER_LOOP_LIMIT` (default 65,536; `spirvEmitterInternal.h:478-500`) is emitted in three forms:
1. **structured loops**: a function-variable counter per loop header, tested on the exit branch
   (`spirvEmitterProgram.cpp:1041`ff., `GuardLoopCondition`);
2. **the dispatcher form** of programs with an irreducible or unsupported CFG: the whole program is one loop over a
   `pc` switch, left at the cap (`spirvEmitterProgram.cpp:575-589`);
3. **compare-exchange loops** of emulated atomics and of 8/16-bit stores to buffer or LDS memory (`AtomicUpdate`,
   `spirvEmitterInternal.h:930-1006`): the update gives up after 65,536 failed exchanges, **and the store is lost**.

Kyty's own counter, `KYTY_DIAG_RT_TRIPS`, counted form 1 only (and only in programs with a loop header). Kyty's README:
"it never fired in our tests, 0 of ~1,950 checks at the gate and in the village, 29.10".

### 4.2 The counter (Kyty 912e9cd8; diagnostic, default off)
- With `KYTY_DIAG_RT_TRIPS=1` every program gets the fault buffer, and forms 2 and 3 add their trips to the same
  diagnostic word as form 1 (form 3 counts only an update that gave up without landing). Each fault pass reports
  `RT_TRIPS frame=… watchdog_trips=…` when anything tripped, and with `KYTY_TRACE_PERF=1` the totals are
  `PERF workaround_hits … watchdog_trips=<trips>/<passes>`.
- A census says what was emitted: `LOOP_CAP_CENSUS programs=… with_cap=… structured_loops=… dispatcher_loops=…
  cas_loops=… uncounted=…` every 256 translated programs, and `LOOP_CAP_SITES` for each program with a dispatcher loop
  or a site that could not count.
- It changes SPIR-V (the switch is in Kyty's shader fingerprint), so the runs use a private copy of Kyty's cache and do
  not touch the shared one.

### 4.3 Result: **the cap never fired** [M v4x-w-diag]
- v4x-w-diag: `run1080.sh long`, 900 s from boot (the T1 intro, the menu, the save load, ~13 min in the river village
  with pad-nojump), `KYTY_DIAG_RT_TRIPS=1 KYTY_TRACE_PERF=1` (plus the other diagnostics of §3/§2, on a private copy of
  the cache: `research/v4/x/kcache-diag`). Fatal none, 3,016 presents, RESTORE OK, RUN1080 OK.
- **`watchdog_trips=0/3063`: 0 invocations reached a cap in 3,063 fault passes**, i.e. over the whole run, intro
  included (the brief's T1 run is inside it: every long run boots through the T1 sequence). No `RT_TRIPS` or
  `WATCHDOG_TRIP` line.
- Coverage (`LOOP_CAP_CENSUS` at 1,792 translated programs): 663 programs carry a cap: 4,530 structured loops, 1,802
  compare-exchange loops, 0 dispatcher-form programs; **0 cap sites that could not count**.
- So in our scenes the cap changes no result, and turning it off (`KYTY_SHADER_LOOP_LIMIT=0`) would change none either.
  What off would change: every module's SPIR-V (cold pipelines once: a new fingerprint), slightly fewer instructions in
  4,530 loops and 1,802 compare-exchange loops (not measured), and a loop that never ends would hang the GPU (device
  loss, TDR) instead of ending at 65,536. The decision is the user's (§6 D-a); the default is unchanged.
- Kyty's maintainers saw the same on their machine (README: "0 of ~1,950 checks at the gate and in the village").
