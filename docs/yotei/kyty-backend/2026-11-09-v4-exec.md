### 1.2 Why the BAR read is slow here, and why the BarCopy threads do not help [C, M]
- The BAR mapping is uncached (write-combined) PCIe memory; `CopyFromWriteCombinedImpl` reads it with streaming loads
  (VMOVNTDQA), 8 per 256-byte step. Kyty's own cost model (written on a 9800X3D + RTX 5070 Ti): ~1.7 µs per span +
  0.54 µs/KiB (~1.9 GB/s). Here [M v4m-k-prof `PERF bar_copy_sizes`, per 5 s]: spans < 4 KiB 1,640 / 1.4 MB / 20 ms;
  < 64 KiB 3,944 / 17.8 MB / 225 ms (≈ 79 MB/s); < 1 MiB 147 / 46 MB / 926 ms (≈ 50 MB/s, with 3 threads). Our E6
  measured 0.09 GiB/s. So a CPU read of BAR on this laptop is 20-40× slower than on Kyty's PC.
- `BarCopyPool` (2 `BarCopy` helper threads) only takes spans ≥ 256 KiB, splits them into three 64 KiB-aligned parts,
  copies part 0 on the calling thread and **spin-waits for the helpers**. The caller is the execution thread (every
  `ReadMemory` request runs there, through `SendCommandSync`, because it changes the dirty/protection state in order
  with the GPU thread's stream). Spans < 256 KiB (98 % of the calls) are copied by the caller alone. The helpers' ~13 %
  busy is their share of the big spans plus a 50-µs spin after each copy. And on this machine three readers are not
  faster than one (50 MB/s with three threads vs 79 MB/s single-threaded in the mid bucket): the BAR read throughput
  does not scale with threads here, so the pool cannot take the cost off the execution thread.

## 3. The GPU copy for host-mapped downloads (`KYTY_PERF_BAR_GPU_COPY`)

### 3.1 Design [C]
- Where: `BufferCache::TryBarDownload`, after its own checks and waits (writes finished: newest granule write tick <
  current tick, not in the open command buffer, not obtained-but-unrecorded; host wait for that tick and its priority
  completions). Instead of `BarBatchRead` (CPU streaming loads from the BAR mapping into a staging vector, then
  `WriteBacking` per interval), when the switch value v > 0 and the download's GPU-written bytes are ≥ v KiB:
  - the same spans (same 2 KiB gap rule) are copied with `vkCmdCopyBuffer` from the guest buffer into a 4 MiB
    host-visible, host-cached staging buffer (`MemoryUsage::Download`);
  - submitted on a **second queue of the universal family** (created at device creation only when the switch is set or
    `KYTY_LIVE_AB` lists it), with a timeline wait on Kyty's master semaphore at the download's write tick, and a fence;
  - the execution thread waits for the fence and publishes every interval from the staging copy with the same
    `SyncTimeline::NoteDownload` + `WriteBacking` calls, in the same order, as `BarBatchRead`.
- The command buffer is not routed through the record thread (only the render scheduler's buffer is), so the copy does
  not wait for the record ring; the queue is not the render queue, so it does not wait for the record worker's pending
  submissions (`SyncQueue`) and does not serialize behind the open command buffer.
- A download larger than the staging buffer, a call off the GPU thread, or no second queue: the mapping is read as
  before.

### 3.2 Why it is exact [C]
- Same bytes: the copy reads the device buffer after the master timeline reached the download's write tick (the
  semaphore wait orders the copy after those writes and makes them available/visible to it, as the end-of-buffer
  host barrier does for the CPU read). No GPU work submitted or recorded after that tick writes these bytes:
  TryBarDownload already refuses downloads whose newest granule tick is the open command buffer or that overlap a
  write obtained but not recorded, and the execution thread records nothing until the copy finished (it waits for the
  fence inside the request). Later already-submitted buffers may run concurrently on the render queue, but they do not
  write these bytes (their granule ticks would be newer).
- Same publish: the same intervals, the same order, the same calls; the dirty-set and protection changes before and
  after are untouched. Only where the CPU reads the bytes from changes.
- Checked in the run: `KYTY_PERF_BAR_GPU_COPY_VERIFY=1` reads every copied download from the mapping as well and
  compares the published intervals (count of mismatches in `PERF bar_gpu_copy`).

### 3.3 KYTY_PERF_BAR_GPU_LARGE (135e5b99)
- With the GPU copy, a read window no longer needs the 1 MiB limit (Kyty set it because BAR reads of large windows
  are slow). The switch raises it to 8 MiB in `ReadRange`, `PlanCallerWait` and `TryBarDownload`, and every download
  above 1 MiB is copied by the GPU. Exact for the same reason as the 1 MiB window itself: a read still gets the
  newest GPU bytes; only how many neighbouring GPU-dirty bytes are published ahead changes.

## 5. Step 2: the frame-start resource-walk waits (diagnosis)

### 5.1 What they are [C, D]
- Kyty's resolve thread walks each draw's and dispatch's resource tables ahead of the execution thread. A walk that
  would read GPU-written bytes is refused there (only the GPU thread may download them), and the execution thread then
  walks it itself, reading the bytes through `ReadMemory` with reader "srt_walker": wait for the producing GPU work,
  then download (host-mapped read, or the copy path when the producer is in the open command buffer or the window is
  too large). Kyty's docs (PERFORMANCE §1, FIXES 2026-11-02): one such dependency at the start of every frame costs them
  8-9 ms ("the 4 bytes are written by the command buffer being recorded, so the CPU really has to wait").
- kyty-prof (v0.1.4, direct ranges off, traced) put them at ~65 ms per frame here (~7.5 ms × 8.5).

### 5.2 Size now [M]
- G2 profile (v4m-k-prof, direct ranges on): SRT-walker downloads 13.1 per frame, 20.5 ms of the execution thread;
  `PERF_RESOLVE_STAGES`: ~46 refused dispatch walks per frame done on the execution thread at ~0.37 ms each (17-20 ms
  per frame), ~41 refused draw walks (2.9 ms), ~260 stale dispatch walks (3.2 ms).
- v4e-ab1, per frame (census): off: 15.7 downloads, 24.9 ms exec (BAR read 8.7 ms, waits for the write tick 6.8 ms in
  1.6 blocking waits, copy path 2.15 downloads / 7.3 ms: 1.0 "open", 1.16 "large"). With the GPU copy: 15.8 ms (BAR
  1.1, waits 6.5 in 1.7 blocking waits, copy path 2.1 / 6.2 ms). With both: 16.0 ms (BAR 1.8, waits 7.5 in 2.3, copy
  path 1.9 "open" / 4.7 ms).
- So after the BAR fix the walker's cost is **~12-14 ms per frame of waiting for GPU results**: ~2 blocking waits for
  an already-submitted producer (~3-4 ms each) and 1-2 producers still in the open command buffer (~2.5-3 ms each,
  submit + wait for the whole open buffer).

**Diagnosis [M + E]:**
- The "65 ms per frame" of kyty-prof is gone on this backend: with direct ranges on (G2) it was ~20 ms per frame of SRT
  walker service, and with the GPU copy it is **~9-10 ms**, of which ~5 ms is the one frame-start read (0.73 per
  frame × 4.8 ms) and the rest ~1-2 further walker reads per frame that wait for a producer.
- The frame-start read is a true data dependency: the producer is in the open command buffer ("open" declines: 1.0
  per frame), so the read submits the buffer and waits for the GPU to finish everything recorded up to it. Exact ways
  to shorten it: (a) submit the producing dispatch's command buffer as soon as it is recorded, when the same address was
  read by a walker in the previous frame (a learned producer list; the wait then overlaps the work recorded between
  producer and reader); (b) resolve that resource on the GPU (Kyty's D7 path, `DecodeIndirectBuffer`). Speculation
  (use last frame's value, check later) is not exact without undo and is out.
- The "large" walker reads (1.3 per frame) and the unservable write-fault windows (0.5 per frame, up to 16 ms) take the
  copy path; `KYTY_PERF_BAR_GPU_LARGE` serves them by GPU copy instead (in v4e-ab1 the walker's copy path went from
  2.1 to 1.9 per frame, "large" to 0).

### 5.4 v4h3's two exec-thread leads (coordinator, 11-09 ~11:00), read against v4e-ab1 [M v4e-ab1]
- **(1) Write-fault pickup delay** (guest job threads queued ~10 ms behind the exec thread's current operation; v4h3:
  182 ms per frame summed, ten threads on page 0x50316b8000). That page is in one of the two 640-KiB buffers
  (0x5031618000, 0x50316b8000) whose write faults published ~320 KiB from BAR at ~7 ms each (§3.5): the
  current operation those threads wait behind is mostly this BAR read. The GPU copy takes it to ~0.5 ms. Guest time
  waiting for the GPU thread to pick write-fault requests up, per frame (`PERF sync_time` invalidate queue): **off
  218 ms → GPU copy 67 ms → both 44 ms** (−69 % / −80 %). So lead 1 is largely served by `KYTY_PERF_BAR_GPU_COPY`.
  The rest is requests waiting behind ordinary operations and the SRT walker's GPU waits (~3-4 ms each).
  Follow-on idea, not built: serve queued fault requests while the GPU thread blocks in a walker's wait for a GPU tick
  (they do not depend on that tick); needs an ordering argument (the request would be served inside an operation
  instead of between two).
- **(2) Deferred end-of-pipe labels published at packet boundaries** (`graphicsRun.cpp:505-511`). `PERF
  label_at_completion` lag, mean of the ~5-s blocks per phase: **off 6.05 ms, GPU copy 5.40 ms, both 5.24 ms**
  (`tools/labels.py`; LARGE alone 65.6 ms is one block with a 7.7-s pipeline compile). Exec idle (`execution_idle`)
  per frame: off 12.4, GPU copy 11.7, both 10.5 ms. Removing the 11-ms BAR reads shortens the lag by ~0.7 ms; the rest
  is the packet granularity itself. Follow-on idea, not built: publish completed labels from the priority-completion
  thread when no packet boundary comes within some time (needs the label write ordered against the GPU thread's own
  writes of the same memory).
