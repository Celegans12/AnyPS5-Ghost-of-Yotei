### 0.2 What it says
1. **Speed gate (≥ 40): 60.9 and 62.0 presents/10 s** [M v4m-k-l1, v4m-k-l2]; 61.4 mean, 1.1 apart. Both runs compiled
   (almost) no pipelines in the world (2 and 0), after a 900-s warm-up that compiled 24 for a camera view v4b-k-w2 never
   had (§2.1).
2. **Stability gate: met.** 1,500 s each, no fatal, no device loss, no hang, presents to the last second, RESTORE OK
   (§3).
3. **Against Kyty standalone, in the same scene: ×0.98.** Overcast, camera C, frames 3500-6500: 63.7 inside AnyPS5
   against 65.0 standalone (same source, same toolchain, direct ranges on) [M v4m-k-l2, v4m-s-clang2on]. Against the
   release (direct ranges off) in matching scenes: ×0.96-0.99 (§2.6). **The ×0.93 of v4b-k-w2 was not real:** that run
   compiled pipelines in the world and was in another scene. Over the whole window from present 1500 our runs read
   lower (×0.93-0.95 of 65.2) because their first ~2,000 presents fall in pad-nojump's jump presses (§2.6).
4. **Screenshots:** `research/v4/g2/sheets/g2-dumps.png` (frame dumps, old backend vs Kyty backend) and
   `research/v4/g2/sheets/g2-captures-A.png` (PrintWindow captures incl. the standalone runs). Visible: no silver sheen,
   no black rock shapes, the cloak dark teal with feathers, no black frames in the world; one open item (a teal and
   orange rock in one view). Details §4; no correctness claim.
5. **Where the rest of the gap sits (profiled pair, §5):** not in Kyty's execution thread (same busy time per frame,
   130.6 vs 133.0 ms, same function mix, same GPU time per frame 61 ms) and not in AnyPS5's HLE (≤ 1 % of the guest
   threads' samples). Z4 holds (cores reserved as standalone). What differs is that Kyty's pipeline waits longer for
   the guest's submissions: execution thread idle 29.4 vs 5.3 ms per frame, command processor idle 51.8 vs 31.3 ms
   (Kyty's own counters). So the remaining gap is on the adapter's side of the guest link (Z1/Z2), small (2-3 % in the
   same scene). This profile cannot say which piece (flip delivery, tracker faults on guest threads, protection
   changes); the pair was not in the same scene.

### 5.3 Reading [E]
- **Kyty's own execution thread is not where the gap is.** It does the same busy time per frame (133 vs 131 ms; after
  removing its spin, ~125.5 vs ~126.4 ms) with the same function mix. The GPU does the same work per frame (61 ms) and
  is ~80 % idle on both. The one exec item that is larger here, BarBatchRead (CPU reads of ReBAR, +3 ms/frame for the
  same bytes), is phase 4's known item on both sides.
- **The HLE is not it either.** AnyPS5's libraries take ≤ 1 % of the guest threads' samples. The guest threads spend
  their time in the game's own poll loops on both emulators, as v4g found.
- **Z4 holds:** the process-wide reservation and the stage-thread pins are the same as standalone's.
- **What differs is waiting for the guest:** Kyty's counters show the execution thread starved for work 29 vs 5 ms per
  frame and the command processor idle 52 vs 31 ms per frame, and the tsamp timeline shows extra execution-thread gaps
  20-60 ms after the present that standalone does not have. That is the pipeline waiting for the guest's next
  submissions, i.e. the adapter's side of the link (Z1/Z2: how fast flips, labels and interrupts reach the guest and its
  submissions reach Kyty's CP). Labels themselves reach the guest faster here (4.6 vs 6.6 ms).
- **Size:** in the same scene the whole gap is 2-3 % (§2.6); in this unmatched pair it reads ~9 %, so part of the
  pair's difference is the scene. Candidates for the adapter piece, not separated here: (a) the flip path (Kyty's flip
  goes through AnyPS5's VideoOut queue and presenter thread; our present lines come from that thread), (b) ~2,150
  tracker faults per present served on guest threads, (c) ×13 protection changes after copies. A same-scene traced pair
  (Kyty's `KYTY_TRACE_SYNC_TIMELINE` plus AnyPS5's VideoOut flip timing) would split them; it was not run (time box).
