## 1. Why the switch-on T1 differed from `t1-ref-1080`

### 1.1 The intro is stepped per present [M]
`tools/introphase.py`: T1 dumps (every 10th present, frames 0-59) of runs whose present rates differ, compared on
160×90 grey thumbnails at the same index and at the best index within ±6 dumps.

| pair | present rate | result |
|---|---|---|
| old 1080p `v4b-t1-off2` vs old **4K** `t1-ref-2` | 14.3/s vs 5.3/s (×2.7) | the same picture at the same index in all 55 non-flat frames (MAD 0.1-0.8: the resolution difference); a wall-clock intro would put 4K's dump i near 1080p's dump 2.7·i |
| old 1080p warm `t1-1080-rep` vs **cold** `t1-ref-1080-cold` | first present at 20 s vs 439 s | frames 0-51 byte-identical |
| old `v4b-t1-off2` vs Kyty `v4b-k-t1e` | 14.3/s vs 29.7/s | the same segments at the same indices, Kyty 5 presents later; the fade-in brightness climbs by the same step per dump on both |

So the game advances 1/30 s of game time per presented frame (by flip count, or by a frame delta clamped at 1/30 s;
the two cannot be told apart at ≤ 30 presents/s, and the game presents at most 30/s). [E] The same holds in the world,
so at ~6 presents/s the world runs at about a fifth of real speed (said in the play guide).

### 1.2 Dumps at every present: one constant offset per run [M]
Two runs with a dump at **every** present 0-599 (`T1_LAST=599 APS5_DUMP_FRAMES_EVERY=1`): `v4r-k-t1dense` (switch on,
28.5 presents/s, so dumping every present does not slow it) and `v4r-o-t1dense` (switch off = old backend, same build,
14.8/s). `tools/t1align.py` looks for a **byte-identical** frame of the dense run within ±30 presents of each dump:

| run | backend | every frame byte-identical to the dense run of its backend? | offset (presents) |
|---|---|---|---|
| v4r-k-t1a, v4r-k-t1b (11-09) | Kyty | yes, 60/60 each | +8 (t1b: +9 for frames 0-1) |
| v4b-k-t1d, v4b-k-t1e (11-08) | Kyty | yes, 60/60 each | +5 |
| t1-ref-1080 (= t1-1080-rep), v4b-t1-off2 | old | yes, 60/60 each | +9 |
| t1-ref-1080-cold | old | yes, 52/52 | +9 |

- Each run is the same fixed sequence of pictures, started a whole number of presents later or earlier, constant over
  the run (one exception: t1b slips one present between its dumps 1 and 2).
- So v4b-k-t1e and v4r-k-t1a (both the G2 DLL) differ in 55 of 60 frames index by index (offsets 5 and 8), and t1b

### 1.4 Can T1 against the old backend be meaningful? Yes, aligned
- **Index-by-index (today's t1_run/frame_diff): no.** The start offset differs between runs (Kyty 5 or 8 presents
  after its dense run, old 9), so fast animations are compared at different moments.
- **A fixed vblank pace would not fix it:** the Kyty runs all ran at the 30 Hz vblank pace and still started 3 presents
  apart.
- **Dumps keyed to the game's own frame counter** help only if the counter starts at the fade-in; a flip count includes
  the black lead-in, which is what varies.
- **What works: a dump at every present plus one alignment offset.** `crossdiff.py` (old vs Kyty) gives PLAN §5.3's
  per-frame statistics; `t1align.py` (Kyty vs Kyty) gives an exact determinism verdict (§2). Proposed §5.3 threshold for
  T1: after alignment, max channel difference ≤ 1 on every non-black frame (measured: 1), to be confirmed at full
  resolution.

## 6. Red-zone exposure (prepared; the measurement run did not get the slot)
- **Why the DLL cannot use Kyty's own trace:** `KYTY_TRACE_FAULT_SITES` lives in Kyty's loader exception handler
  (`src/loader/runtimeLinker.cpp`), which is not in the DLL; the seam's `handle_fault(address, access)` carries no
  context (`FaultSiteScope(0)` in `kytyBackend.cpp`).
- **Tool, AnyPS5 side:** `local/v4-r` 3a979863e21 (worktree `AnyPS5-scratch/v4-r`, build `build-local` with the same
  DLL md5; pushed as `backup/local/v4-r`): `APS5_KYTY_FAULT_SITES=1` counts every fault the backend serves in
  AnyPS5's head exception handler by faulting RIP (lock-free 64 k-entry table), with the guest-thread share and how often
  RSP is 8 mod 16 (no frame below a call), and prints per-module totals and the top 64 sites every 60 s. Off by default;
  not for integration.
- **Analyser:** `research/v4/r/tools/rzsites.py <err.log>`: for each top site, the containing function (eboot.exe: the
  game ELF's `.eh_frame_hdr` table mapped through the PE layout, ELF vaddr = RVA − 0x10000; other PE modules: `.pdata`),
  capstone disassembly, the RSP delta per instruction over the CFG, and byte-level liveness of the 128 red-zone bytes.
  Exposed = the function addresses memory below RSP and some red-zone byte is live at the faulting instruction (as Kyty's
  patcher decides). MS-ABI modules (system DLLs, `kyty_gpu.prx`) have no red zone.
- **Static result [M]:** 401 of 51,054 game functions (0.79 %) address the red zone (no unknown RSP arithmetic among
  them). Example of a real exposure candidate: eboot `+0x163e310` keeps a 32-byte AVX value at `[rsp-0x28]` across a
  loop whose body stores to guest memory (`mov word ptr [rax], dx`): a tracker fault on that store would overwrite the
  value. Whether such functions take tracker faults is what the census measures.
- **Run, ready:** `research/v4/r/chain-r3.sh 0` (tag `v4r-k-rz1`: run1080 long on the tool build, the §3 recipe, 600 s,
  `APS5_KYTY_FAULT_SITES=1`, then rzsites into `logs/rzsites-v4r-k-rz1.txt`). Exposure = the faults at exposed sites as a
  share of the ~13,000/s served on guest threads.
