## 2. D-f: `KYTY_FIX_RING_DEAD_DOWNLOAD`
What the switch changes [C `bufferCache.cpp` `DropDeadRingBytes`]: on a CPU write fault into a GPU-modified page of the
data ring (0x2002600000-0x2010000000), the G2 rule drops the page's GPU bytes written before the previous frame began.
With the switch on nothing is dropped and the fault goes on to the ordinary download (the +-4 MiB read window, by the
GPU copy on this build). It is a `KYTY_LIVE_AB` switch; default 0.

### 3.4 Depth textures read while their fast clear is pending (lane v4x's step 4, row 24 of its list)
**The numbers are print thresholds, not limits.** The counter is a 64-bit atomic; a `PENDING_CLEAR_READS` line is
printed at powers of two and at every multiple of 4,096 [C `descriptors.cpp` `NotePendingClearRead`]. 65,536 is the
last line vx2-w-census printed (frame 8174 of 8,506), so its true count is between 65,536 and 69,631; vx2-w-census2's
is between 73,728 and 77,823 (last line at frame 6313 of 6,586). Rates between lines [M]: 9.0 such binds per frame of
116 depth-texture binds (7.7 %) at the river village with pad-nojump [vx2-w-census, frames 4988-8174]; 14.0 of 118
(11.9 %) with the camera turned [vx2-w-census2, frames 1333-6313]. `NO_OUTPUT_DRAW_DROPS` is capped the same way: its
line is printed up to the 4,096th dropped draw and then every 65,536, so "260 of 4,096" is the state at frame ~1003
(mostly the load); no later line was printed, so each run dropped fewer than 65,536 no-output draws in all.

**What such a read returns today: the host depth image as the last draws left it, i.e. stale depth, not the clear
value** [C, Kyty `v4/x2` 797c6cae]:
- A fast clear is only a flag. When a compute shader or a fill writes a depth surface's HTILE, Kyty takes the write as
  a clear and sets "cleared" for the slice (`renderCompute.cpp:92` the read-modify-write shader b25b01ff1361e795,
  `renderCompute.cpp:131` and `bufferCache.cpp:3287` write-only fills; `TextureCache::ClearMetaRmw/ClearMetaWrite`).
  The host depth image is not touched.
- The flag is consumed at the surface's next bind as a depth target: the render pass then loads with a depth clear

### 3.7 The exact variant: how it would be built and gated (lane v4x3; not built, for a later lane)
**Where the clear has to land.** Not at the left-out expand draw: no expand draw comes before any of these episodes
(`after_expand=0` for the 1024x1024 and 128x128 depths in both runs), because on the PS5 none is needed: the sampler
reads through the HTILE. The resolve has to happen at the texture bind, in `RenderExecutor::FindResolvedTexture`
(`descriptors.cpp`, where `PendingClearCheck::OnTextureBind` already gets `r128`, `MetaCompress()` and
`MetaAddr() << 8`): when the descriptor is 64-bit, carries MetaCompress and its metadata address is the image's own
HTILE (`image.info.metadata.range.address`), and `TextureCache::IsMetaCleared(htile, slice)` is true, apply the clear
to the host slice before the bind is recorded, then consume the flag with `TouchMeta(htile, slice, false)` (the same
call the depth-target bind makes at `renderDraw.cpp:960`). A plain descriptor must keep today's behaviour: the PS5
then reads raw memory (the 1920x1080 case), so the 312 plain binds stay stale on purpose.

**The value.** Two levels, cheapest first:
1. *Whole-slice clear with the recorded value.* Store DB_DEPTH_CLEAR at the dispatch that set the flag (the
   diagnostic's `pendingClearNote.h` already captures it for `cs_rmw` and `cs_write`; the fill path has the word) in
   the surface meta next to the clear mask, and clear the slice with `vkCmdClearDepthStencilImage` outside a render
   pass (the scheduler has to end the current pass, as `Image::Download` does in the diagnostic). Exact only if the
   HTILE write cleared every tile and the TC returns DB_DEPTH_CLEAR for cleared tiles.
2. *Per tile from the guest HTILE* (the expand the PS5's texture unit does on the fly): a small compute or full-screen
   depth-export pass that reads the guest HTILE words for the slice and writes the decoded value (ZMask 0 = cleared,
   Z range = the clear value) only into cleared 8x8 tiles. Exact for partial clears too; it needs the HTILE layout
   (Kyty's `htile` addressing used by `WORKAROUND_HTILE_FULL_RANGE`) and costs a pass per stale bind episode
   (two 1024x1024 slices about every second frame here).
Level 1 first; the diagnostic tells whether level 2 is needed (any texel left differing after level 1).

**Switch and cost.** `KYTY_FIX_PENDING_CLEAR_BIND`, a `KYTY_LIVE_AB` runtime switch, default off; not a shader
