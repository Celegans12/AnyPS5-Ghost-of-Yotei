# v4 seam (2026-11-08): where Kyty's GPU backend connects to AnyPS5, and whether anything blocks it

Lane v4s, PLAN v4 phase 0, steps 0b (seam map) and 0c (memory model fit). Code reading and design only: no build, no
game run, no machine job, no git write, nothing posted. PLAN/STATE/HANDOFF untouched.

- Kyty: KytyPS5-Yotei v0.1.4 source, `research/speed/v3/kyty/src/yotei/src` (GPL-2.0-or-later). Run evidence from the
  kyty-prof runs in `research/speed/v3/kyty/runs/` (w2 = the 48.1 presents/10 s run).
- AnyPS5: yotei/best `72af1e5ea23`, `AnyPS5-scratch/yb-combo` (read only).
- The full seam table and file lists: `research/v4/seam/adapter-spec.md` (this report cites its sections as spec §N).
- Tags: [M] read in code or measured (source named), [E] estimate (reasoning named), [D] Kyty's docs or comments.

## 0. The answer on one page

- **No blocker in 0b or 0c.** Kyty's graphics subtree depends on the rest of Kyty through a narrow, countable set:
  22 `kernel/memory.h` functions (+2 constants), 5 shader-IR read hooks, the event queue, 4 clock functions, 3 param.sfo
  getters, error codes, and its own `common/` (which depends on nothing else) [M grep, spec §4.3, §5]. Everything else
  in `src/graphics` (≈270 of 288 files, ≈130k lines) comes over unchanged.
- **The seam is the outer edge, as PLAN wanted, at four places:** AnyPS5's driver entry points (36 `extern "C"` entries
  in one file plus `Eq/` and the static table), AnyPS5's VideoOut ↔ driver hook set, guest memory, and a handful of small
  services. AnyPS5's `libSceAgc` builder, `libSceVideoOut`, window, input and HLE all stay.
- **Three things must be done right; none is a research question:**
  1. **Memory.** AnyPS5 keeps un-aliased direct memory as *private* pages and has no always-valid second view of guest
     memory; Kyty reads and writes guest memory through one such view while it protects the guest pages. Fix: a "kyty
     mode" of AnyPS5's direct memory: one section for all of it, one backing view, no private ("resident") pages. About
     200 lines in `libkernel/DirectMemory` and `libc/GuestArena`, behind the switch (spec §4.2).
  2. **Who owns page protection.** AnyPS5's exception handler is first in the chain, and its `GuestArenaHandleWrite`
     would treat a Kyty-protected shared page as its own and silently re-open it. Kyty's handler must sit at the head
     of the chain, and AnyPS5's map/unmap/mprotect paths must tell Kyty first (spec §4.4, §4.5).
  3. **Two packets.** AnyPS5's builder matches Kyty's command processor packet for packet except for
     `sceAgcCbReleaseMem` (AnyPS5 emits a real `RELEASE_MEM` 0x49 that Kyty's CP has no handler for; AnyPS5's HLE
     JobManager emits it too) and the rendering wait (4 dwords against Kyty's asserted 7). Both are few-line CP patches.
     **Neither builder has to come along** (spec §2.3).
- **The red zone is not a G0 blocker.** Kyty ships its red-zone patcher *off* by default, and its measured 1,505 s run
  on this machine ran without it [M w2 `run.txt`]. AnyPS5 already takes guest-store faults on aliased direct memory
  today. Two mitigations exist or are cheap: AnyPS5's relinker already has `--frame-red-zone` (narrower than Kyty's
  per-instruction patch), and Kyty's patch can be ported to the relinker in 3-5 days. Do it in phase 3, after measuring
  exposure (§2.2).
- **Size:** ≈2,800 new adapter lines + ≈700 changed AnyPS5 lines + ≈600 lines of Kyty patches (≈6,000 Kyty lines of
  window, input, overlay and VideoOut HLE dropped). **18-25 agent-days to "boots to the title"**, three lanes, about
  1.5-2 weeks of calendar [E §4]. That fits PLAN phase 1 (title at week 2-3).

Reverse direction (AnyPS5 must call into Kyty): `RenderContext::MapMemory/UnmapMemory` on every mapping change,
`HandleFault` from the exception handler, `InvalidateMemory` on host writes, a read-sync on host reads, and a re-apply of
watch protection after a guest `mprotect` (spec §4.4).

### 1.2 AGC submission, and whether a builder must come along

- **Submission.** Kyty: `AgcDriverSubmitDcb` → `GuestGpu::Submit(span, {})`, ACBs → `SubmitCompute(queue, span)`
  (`libs/agc.cpp` l.4116-4285). AnyPS5: every submit export and the HLE JobManager end in `AgcDriver::Submit(packet,
  queue)` in `Execution/src/Driver/EntryPoints.cpp`. One branch there [M].
- **Builders.** Both emulate `libSceAgc` (Kyty in `libs/agc.cpp`, AnyPS5 in `libs/prx/libSceAgc`), and both mirror the
  console's private NOP encodings (the custom code in header bits 2-7: flip 0x17, wait 0x06, context state 0x1A,
  markers 0x0B/0x0C, dispatch reset 0x09) and the `SET_UCONFIG_REG 0x342` internal-data tags. Packet by packet they match
  (spec §2.3), with two exceptions:
  - `sceAgcCbReleaseMem`: AnyPS5 writes a real `IT_RELEASE_MEM` (0x49); Kyty writes its custom `R_RELEASE_MEM` NOP with
    the same 7-dword payload, and its dispatch table has no 0x49 entry [M `pm4Dispatch.cpp` l.150-236]. Fix: register
    0x49 to the same handler.
  - `sceAgcDcbWaitUntilSafeForRendering`: AnyPS5 writes 4 dwords (`0xc0021018`), Kyty's handler exits unless the header
    is the 7-dword `0xc0051018` [M `pm4Handlers.cpp` l.2652]. Fix: accept both.
  - AnyPS5 can also emit 0x1d, 0x1e, 0x45, 0x91, which Kyty lacks, but only from HLE functions Kyty does not implement.
    Yotei calls none of them: Kyty's w2 run had three unresolved imports, all `NpSessionSignaling` [M `w2/stdout.log`].
- **Shaders.** Kyty's `AgcCreateShader` registers the program with `ShaderMapUserData`; AnyPS5's `libSceAgc` already
  calls `AgcDriverRegisterShader_nid_postfix` at the same point. The adapter maps one onto the other; AnyPS5's
  ABI-resolution hooks become no-ops.
- **Verdict:** keep AnyPS5's builder (the HLE layer stays identical on both backends, which 0d needs), patch Kyty's CP
  in two places, and confirm with an offline packet census at the start of phase 1 (spec §9.1).

### 1.3 EOP, labels, flips, event queues

- Kyty raises EOP interrupts itself (`RenderContext::TriggerInterrupt(event, context_id)`, events registered by
  `Sync::AddEqEvent`). Under the switch, AnyPS5's `sceAgcDriverAddEqEvent/DeleteEqEvent/GetEqContextId` route to Kyty's.
- **HLE difference [M]:** `sceAgcDriverGetEqContextId` returns the queue id on AnyPS5 and the interrupt context id on
  Kyty (each trigger also kept as a pending event). The game sees Kyty's behaviour under `kyty`.
- Labels written by the GPU: Kyty's CP write-through (`TryCpWriteThrough`) handles labels in protected pages. No seam.
- Flips: spec §3.2. EOP flips (`sceVideoOutSubmitEopFlip`) exist in AnyPS5, not in Kyty, and Yotei does not call them.

### 1.4 VideoOut and presentation: whose window, whose swapchain

- AnyPS5's VideoOut owns the window (SDL2), buffers, events, flip queue and pad input, and already hands the driver a
  `PresentationWindow` (instance extensions + a `createSurface` callback + drawable size) [M `Presentation.hpp`]. That is
  what Kyty's `WindowContext::CreateVulkan` needs instead of its SDL3 window.
- Kyty's flip is recorded **in the command stream** (`R_FLIP` → `PrepareFlip` copies the display image into a presenter
  frame at that point; presented after the tick). Recommended bridge (spec §3.2): Kyty's `VideoOutDriver` class is kept
  as an interface and implemented over AnyPS5's `IVideoOutput` (reserve, rendering waits, `GpuReady`), AnyPS5's presenter
  thread still calls `AgcDriverPresentBuffer`, which presents the frame Kyty prepared in-stream. One AnyPS5 interface
  addition: `IVideoOutput::Buffer(index)` so the bridge knows the display buffer at the flip.
- Swapchain and presenter: Kyty's, on AnyPS5's window. Window, input, system overlay and Kyty's `sceVideoOut*` HLE
  are dropped (≈6,000 lines).
- **Tooling must keep working:** the bridge emits the `[gpu] frame_NNN.bmp:` frame dumps (`APS5_DUMP_FRAMES`) that
  `t1_run.sh` waits for, and the `[present] N presents` line `game_run.sh` counts.

### 1.5 Resource registration

Both stub it (AnyPS5 `Resource/src/Registration.cpp` returns "unavailable"; Kyty's `AgcDriverRegister*` likewise).
No seam.

### 1.6 Threads and priorities

Kyty's four GPU stage threads are its own (`common/threads`), pinned to whole cores, with the rest of the process kept
off them by process CPU sets (`Thread::ReserveCores`). AnyPS5 does not pin guest threads by default
(`libkernel/Pthread/src/Thread.cpp` l.850), so this works as on Kyty. The fault path identifies Kyty's GPU thread with
`GuestGpu::IsGpuThread()`; guest-thread detection uses AnyPS5's pthread lookup.

### 1.7 Shader and pipeline caches

Kyty writes `_PipelineCache/<title>.bin` (Vulkan pipeline cache) and `<title>_<ver>.bda_granules` **relative to the
working directory** (`pipelineCache.cpp` l.1438, `bufferCache.cpp` l.220), and its journals/archives through `Config`.
Run from a fixed Kyty cache root (or a 2-line path patch). The 158 MB warm cache of the w2 runs can seed it if the SPIR-V
fingerprint matches, which saves the cold compiles in phases 1-2 [E].

### 1.8 Third party

Kyty's graphics + common need fmt, xxHash, nlohmann_json, spdlog, magic_enum (not in AnyPS5), and Vulkan-Headers, VMA,
SPIRV-Headers/Tools, ZArchive, stb, tracy (in both, versions to align in 0a). SDL3 and imgui are not needed. Both build
as C++20 [M CMake].

## 2. 0c: memory model fit

### 2.1 The two models, and the fit

| | Kyty | AnyPS5 |
|---|---|---|
| direct memory | one section for all of it, guest ranges are views | one section per allocation; **un-aliased ranges are private pages** ("resident", `MEM_WRITE_WATCH`), demoted to views when a second alias appears |
| emulator access | a second, never-protected view of the whole section | none global; per-run aliases on demand (and they demote resident pages) |
| CPU write detection | page protection + faults | write watch on private pages; **protection + faults on aliased (shared) pages** already today (`WindowsMappings::Collect`, "arm shared memory write tracking") |
| GPU told about mappings | ~20 kernel call sites | none needed so far; the `MappingChange` bracket exists |

[M spec §4.1.] Kyty's tracker cannot run on resident (private) pages: its downloads write into the backing view, and a
private page has none. With the **kyty mode** (one section, one backing view, resident off; spec §4.2) every Kyty
memory function has a direct AnyPS5 answer, mostly a lookup in `DirectMemory`'s mapping table plus a `memcpy` from the
view. Cost: committed section pages cannot be decommitted, so commit charge follows the direct-memory high-water mark;
Kyty commits the whole size up front, so this is no worse [E].

**Aliases** (two guest ranges on one physical range): Kyty's tracker works per virtual page, so a GPU write through one
alias does not protect the other. That is Kyty's own behaviour, unchanged by the seam.

### 2.2 (1) The SysV red zone

- **Kyty's patcher** is `loader/guestInstructionPatcher.cpp` (from shadPS4, GPL-2.0-or-later), run at load time by
  `loader/runtimeLinker.cpp` only with `--redzone`, **default off**; the launcher hides the switch [M].
  - **How it picks functions:** function starts from the image's `.eh_frame_hdr`; Zydis decode of each function; a
    function "uses the red zone" if an operand reaches below RSP within 128 bytes. A per-byte liveness analysis over
    the CFG falls back to "all live" on indirect branches, unknown RSP arithmetic or undecoded branch targets.
  - **What it patches:** every memory instruction where a red-zone byte is live and that does not itself use RSP. The
    site is moved to a trampoline `lea rsp,[rsp-128]; insn; lea rsp,[rsp+128]; jmp back`, so a fault's exception frame
    lands below the red zone. Short or unrelocatable sites stay unprotected and are only counted.
- **Kyty runs Yotei without it.** The measured run (`w2`: 1,505 s, 48.1 presents/10 s, river village) had no `--redzone`
  and no crash [M `runs/w2/run.txt`]. So guest-store faults into tracked pages from red-zone-live code are rare in this
  scene, or harmless there. That is evidence, not proof.
- **AnyPS5 already has a relink-time framer:** `relinker --frame-red-zone` (`codegen/src/x86/RedZoneFramer.cpp`). It
  frames whole leaf functions of certain prologue shapes and skips the rest (documented in `docs/dev/debt/relinker.md`
  l.18-21). Its coverage is narrower than Kyty's.
- **Can our relinker apply Kyty's patch at relink time?** Yes. It has `.eh_frame` function bounds, a stub/trampoline
  writer with RIP-relative relocation (`--to-intel`) and an overlap check against game patches. Missing: Kyty's
  decode-and-liveness pass, which can come with Zydis or be ported onto the relinker's own decoder. 3-5 agent-days with
  tests [E].
- **HLE has the same exposure:** our `APS5_VABI` functions are `sysv_abi`, built without `-mno-red-zone` (Kyty's too).
  GCC may keep values below RSP in such leaf functions even on a Windows target. A `-mno-red-zone` flag on the prx
  libraries removes that for our own code.
- **Recommendation:** phase 1 with no red-zone patch (as Kyty). Measure the exposure with Kyty's own fault-site trace
  (`KYTY_TRACE_FAULT_SITES=1`, spec §9.2). Then, in phase 3, port the patch into the relinker (or run
  `--frame-red-zone` if it covers the hot sites).

### 2.3 (2) Exception handler coexistence

- AnyPS5 installs `ReportCrash` first in the chain at libc start (`CrashReport.cpp` l.731). For an access violation it
  asks `GuestArenaHandleWrite` / `HandleRead`, then reports and ends the process.
- Kyty's own installer appends (`AddVectoredExceptionHandler(0, …)`) and would never be reached.
- Worse, on a shared (view) page `GuestArenaHandleWrite` finds a writable guest view and re-opens the page. It would
  swallow the write Kyty protected the page for: a silent stale-GPU-data bug, not a crash.
- **Rule:**
  - the adapter installs its handler at the head of the chain after libc's;
  - it serves faults on pages Kyty's tracker owns (`RenderContext::HandleFault` inside Kyty's retried-fault scope);
  - it passes everything else on.
  - AnyPS5's own shared-page arming never happens under `kyty`, because only the old driver's `Collect(clear)` arms.
- Lock rules (spec §4.5):
  - Kyty's fault path never takes AnyPS5's `MappingMutex`;
  - AnyPS5 mapping changes take the adapter's protect lock exclusive and call `UnmapMemory` first;
  - GPU-thread callbacks into AnyPS5 are watched for the equeue-mutex case.

### 2.4 (3) HLE code and Windows APIs writing into protected pages

- **Kyty:** `Memory::InvalidateMemory` before `ReadFile`-style calls, 6 sites in `kernel/fileSystem.cpp`.
  `GuestBytesForKernelRead` copies image-watched bytes to scratch before a kernel-mode read. `GuardedGuestCopy` is used
  only by a diagnostic [M].
- **AnyPS5 already has more:**
  - `HostWrite` / `GuestArenaBeginHostWrite` and `GuestArenaPrepareHostRead` at ≈25 kernel-mode I/O sites: Stdio,
    sockets, Net, JobManager, FreeType, Process, DescriptorControl, Open, Aio, Apr, Jxr;
  - hook slots for both (`GuestArenaSetHostWriteHook/SetHostReadHook`).
  - The adapter maps them to Kyty's `InvalidateMemory` and to a read-sync.
- **One Kyty patch is needed:** while a host access is open (async I/O included), the tracker must not write-protect
  those pages again. AnyPS5's own arming already skips pages with open host writes.
- **Phase-1 pass:** a handful of files do kernel-mode I/O without a guard: SharedMemory, FileEvent, Ssl, VorbisDec,
  Audio3d, AudioOut2SpeakerArray, LoadExec and others. Most of them use host buffers; check them once.
- **User-mode HLE copies** (memcpy) fault and are served like guest accesses.

### 2.5 (4) Fallback if protection proves unsafe: write-watch-driven dirty flags

1. Kyty's `PageManager::Protect` becomes a no-op; its tracker bitmaps stay.
2. **CPU writes:** at each submit (and at Kyty's existing "publish CPU-dirty regions" points), `GetWriteWatch` with reset
   over the tracker's registered regions, then mark the written pages CPU-dirty.
   - This needs AnyPS5's resident (private, write-watched) mode **on**, the opposite of §2.1.
   - Backing reads then come from the guest addresses themselves; that is safe because nothing is protected.
   - Aliased pages have no write watch: treat them as always dirty, or use AnyPS5's compare-when-shared.
3. **GPU writes:** with no no-access pages, a CPU read of GPU-written memory would see stale bytes.
   - Every GPU-dirty range must be downloaded before the label, interrupt or flip that lets the CPU look.
   - That generalizes Kyty's eager hot-window readback to all GPU-dirty ranges.
   - It is the old backend's copy-back cost class, while keeping Kyty's copy-in and translation gains.
- **Exactness:** fine under the console contract (CPU writes are visible to the GPU from the next submit).
- **Cost:** unmeasured. Hundreds of 4 MiB regions × ~100 submits per frame is too many calls, so the collect has to move
  to coarser points (labels the GPU waits on).
- **Build:** 5-8 agent-days. Build it only if phase 1 shows protection to be unsafe.

### 2.6 (5) Single Vulkan buffers above 2 GiB

- **Fixed allocations:**
  - BDA page table: one 768 MiB device-local buffer;
  - upload ring 512 MiB;
  - device/stream/download rings 128/64/64 MiB;
  - fault buffer about 24 MiB;
  - fallback imports in 2 MiB granules.
- **The open one: guest buffers joined on overlap have no size cap.** Kyty's own diagnostic mentions a 2,064 MiB buffer
  [M `bufferCache.cpp` l.1942].
- On 1.008 in the river village Kyty held 2,630 buffers, 1,052 MiB in all, and 5.9 GB of images [M kyty-prof w3].
- Descriptor ranges are clamped to `maxStorageBufferRange` (read-only ranges to 256 MiB).
- **Risk for Pipodi-class cards** (RTX 4090 wrong values above 2 GiB): only through a joined buffer that large. Mitigation
  if it shows: a 1 GiB join cap (a ~30-line patch).
- Not needed on our 16 GB laptop GPU for phase 1-2.

### 2.7 (6) RAM and VRAM

- **Kyty standalone:** 22-28 GB RAM, 9.0 GB VRAM [M kyty-prof / PLAN].
- **Under `kyty`, AnyPS5 loses:**
  - the old driver's 8.8 GB host import;
  - its staging, shadow and texture caches.
  These exist only if the old `Driver` is constructed.
- **Guest memory is the same in both emulators.**
- **Kyty adds its own:**
  - pinned fallback granules, up to 3 GB (pinning, not extra RAM);
  - host rings, about 0.6 GB;
  - VRAM about 9 GB, which on NVIDIA/Windows also counts toward commit.
- **Expected:** about Kyty's 22-28 GB [E]. To be measured in phase 2 with the existing memory-accounting tools.
- **Hard rule:** no path may construct the old `Driver` under `kyty`. Today `AgcDriverStaticTable` and the presentation
  hooks (`AttachWindow`, `RegisterVideoOutput`, `PresentBuffer`) construct it, and `StoreGuestLabel` goes through the
  old driver's write tracker. All are gated in spec §2.1. Both backends live at once would not fit in 32 GB.

## 5. Recommended seam

1. **AGC:** keep AnyPS5's `libSceAgc` and `libSceAgcDriver` exports. Switch in `EntryPoints.cpp`, `Eq/`, `Lifecycle.cpp`
   (static table) to Kyty's `GuestGpu`, `Sync` and `ShaderMapUserData`. Patch Kyty's CP for 0x49 and the 4-dword wait.
2. **Presentation:** keep AnyPS5's `libSceVideoOut`, window and input. Implement Kyty's `VideoOutDriver` over AnyPS5's
   `IVideoOutput`, with the copy still prepared in-stream at `R_FLIP`. Kyty's swapchain and presenter run on AnyPS5's
   `PresentationWindow`. Fallback: Kyty's whole `videoOut.cpp` (option V-A in spec §3.2).
3. **Memory:** Kyty's `kernel/memory.h` API as a shim over a kyty mode of AnyPS5's direct memory: one section, one
   backing view, no resident pages. Kyty owns page protection through a head-of-chain exception handler. AnyPS5's
   `MappingChange`, `mprotect` and host-I/O hooks call into Kyty first.
4. **Vendoring:** `src/graphics` + `src/common` as a pinned subtree compiled as one static library. About 10 files patched
   (spec §7.2), the window/input/overlay/VideoOut-HLE files dropped (§7.3). Shim headers keep Kyty's include paths, so
   upstream files compile unchanged.

## 6. What this changes in the plan

1. **Where the adapter lives.** PLAN §4 phase 1 says "adapter in `libSceAgcDriver/`" and "with the switch off, the build
   is byte-for-byte today's driver".
   - The adapter does live there, but the kyty mode also touches `libkernel/DirectMemory`, `libc/GuestArena` and one
     virtual in `IVideoOutput`, all gated.
   - The off-switch guarantee should read **"behaviour unchanged, T1 MATCH"**: the binary changes.
2. **The red zone moves from a G0 question to phase 3.** First measure exposure with Kyty's fault-site trace; then the
   relinker port or `--frame-red-zone`. Optional now: `-mno-red-zone` for the prx libraries. That is a build-flag
   change that also touches the frozen backend's code generation, so it needs the user's OK.
3. **Phase 1 starts with an offline packet census** (half a day to a day) before the CP patches.
4. **For 0d, two guest-side differences:**
